ROCm Takes the Lane, InferSSD Takes the Test

19 Nov 2026·Jack’s Corner · Benchmarks·By Jack·Published

Today was a bench day on the AI-Server, the Dell Precision 5860 that runs Fritz, and it produced three results worth writing down: a graphics stack swap that earned its place, a trust check that passed clean, and a head-to-head that a promising engine lost. The loss is the most useful of the three, so it gets the most space.

ROCm takes the main lane

Fritz’s main lane, the one that runs qwen3-coder:30b for his deep work, has been on Vulkan since the Linux migration. Vulkan runs on just about anything, which made it the safe first choice. ROCm is AMD’s own compute stack, and on AMD’s own card it ought to win. Today it did, on the bench harness we froze in October: same coding task, same prompts, same counting.

ROCm generated at 45.88 tokens a second against Vulkan’s 37.56, about 22 percent faster, with the outputs checking identical. That cleared the bar set in advance, so the lane swapped at 11:37 this morning, Mountain time. The swap carries one standing rule, the kind you only learn by being bitten: every future Ollama version change has to re-extract the matching ROCm add-on, or the lane quietly falls back to the slow path and nobody notices until the numbers sag.

The first live landing test, pressing Enter in Fritz’s window over the remote desktop, put first audio at 31.89 seconds on a cold first press, then 21.67 and 21.37 seconds warm. Our house rule is three clean landings before a fix counts as done, so the swap stands at one of three: in service, not yet called proven.

The morning check: trust battery, 4/4

Before any bench work, Fritz sat his trust battery, the standing set of “where did you learn that?” checks that grade whether his answers trace to things he actually read. He passed 4/4. It is the smallest result of the day and the one the whole project stands on: a local assistant whose numbers can be audited is worth more than a fast one whose numbers cannot.

InferSSD meets llama.cpp, and loses honestly

The main event was a visitor. InferSSD, from WiCi, is an inference engine built on llama.cpp with one idea: stream a mixture-of-experts model’s experts from SSD on demand, so a model far larger than your memory can still run. It is Apache-2.0, it lists ROCm support, and almost nobody has published numbers for it on AMD hardware. We installed release 261119.309 from source this morning. Two install details are worth keeping. The HIP SDK went in as a user-space tarball, no sudo anywhere. And the installer had to be kept away from the box’s NVIDIA cards, because its backend detection prefers CUDA whenever it can see an nvidia-smi binary; a shim PATH with no nvidia-smi in it got us the ROCm build we came for, 456 build steps, clean.

The test file was Qwen3.6-35B-A3B in its UD-Q4_K_XL quant, about 21 GB on disk, run on both engines back to back against a frozen 5,266-token prompt. Decode was measured the way WiCi’s own tables measure it, over tokens 129 to 256, so the comparison happened on their home ground as well as ours.

llama.cpp, a current upstream build in its fit-to-VRAM mode, decoded at 70.6 tokens a second and prefilled at 2,465. InferSSD decoded at 37.4 and prefilled at 940. It cleared the 30 tokens a second bar we had set for “interesting” once its expert cache warmed, and it still lost decode by 1.9x and prefill by 2.6x. Its cold first run showed what the warming costs: 22.1 tokens a second, 62.8 seconds to the first token, and 3.87 GB read from the SSD on that run alone. llama.cpp read essentially nothing from disk after an 8 second load, because the whole model was already resident.

Correctness came out identical on both engines, two of three on the frozen set, down to the same sentence on the factual prompt. The coding prompt failed on both in the same way: the model’s reasoning consumed the whole token budget and never emitted code. That is a property of this thinking model, not of either engine, and the parity matters. InferSSD is not making things up; it is just slower here. It also showed one genuine rough edge, intermittent server errors on short requests from its elastic VRAM path. The correctness set needed retries to finish; llama.cpp needed none.

Verdict: feasibility only, by the rules written before the run. A 21 GB model fits this card and fits system RAM several times over, so the SSD streaming had nothing to do except pay for itself. What the result does prove is the ROCm path, end to end, which was genuinely unknown this morning. It says nothing yet about the case the engine is actually built for.

The permission trap

The day also produced the kind of failure this site exists to write down. Mid-bench, the desktop session on the tower ended, the login greeter took the seat, and the GPU device permissions flipped with it. Every new ROCm process suddenly got permission denied opening the device, while everything already running kept working, which is a fine way to waste an hour if you let it. Our account had never been in the render or video groups; it had been borrowing GPU access from the graphical session all along. One command fixed it permanently, and the proof closed the loop: Fritz’s lane loaded his 30B model at full VRAM residency and answered. The lesson, for the record: on a box that works headless, GPU access should come from group membership, never from whoever happens to hold the seat.

What is on the wire

Which leaves the real test. Qwen3.8-Flash-Next is a 177 billion parameter model with about 6 billion active per token, and it is the model on InferSSD’s own box art. Its UD-Q4_K_XL quant is 111.3 GB, and WiCi lists that exact file as tested. The plan is approved, the four shard hashes were pinned in writing before the download started, and the file is coming down the wire as this post is written. The test runs it two ways: with the machine’s full 128 GB of RAM available, and with RAM capped at 32 GB, the regime the engine actually claims. Those numbers get their own post.

Method and sources: bench harness and frozen prompts kept with the lab records; Ollama 0.40.16; llama.cpp b12549 built from upstream with HIP; InferSSD 261119.309 from WiCi’s installer; model file unsloth/Qwen3.6-35B-A3B-GGUF, UD-Q4_K_XL, sha256 verified against the publisher’s metadata before the run. All figures measured on the AI-Server described above, 19 Nov 2026.
