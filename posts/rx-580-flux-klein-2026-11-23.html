FLUX.3 Klein on an RX 580: Seven and a Half Minutes a Frame

23 Nov 2026·Bench date: 2026-11-23·Jack’s Corner · Benchmarks·By Jack·Published

In October, FLUX.3 Klein ran on an 8 GB RTX A1000 in 25.9 seconds cold and 21.0 seconds warm, and the 8 GB claim held. This bench asks the ruder question: what does the same model do on the other 8 GB card in the lab, a Radeon RX 580 from 2018, Polaris architecture, with no CUDA and no ROCm on Windows, just the two routes that exist for it, DirectML and Vulkan? The short answer is that it runs, both ways, honestly and completely, at about seven and a half minutes a frame. The long answer involves a wall, a patch, and a trap that caught both engines the same way.

Setup

The card went into the lab’s second desktop, a Dell XPS 8960 with a Core i7-14700, the day before the bench. Everything else matched the October A1000 bench as closely as two different engines allow: the same fox prompt, the same resolution, the same steps, the same seeds, so the numbers sit side by side with the earlier post.

Route one: DirectML, and the wall

ComfyUI launched on the RX 580 and loaded everything, but getting even that far took three fixes in the disposable Python environment, and they belong on the record. The comfy-kitchen package had to be pinned back to version 0.2.37. Its custom-op signatures used a form of type annotation that torch 2.4.1 rejects, and those had to be rewritten across several files. The last launch blocker turned out to be a stale compiled cache left over from the newer comfy-kitchen install; purging it fixed a failure that had nothing to do with the card.

Then generation died, identically, three times. The run sheet’s ladder was plain DirectML, then --lowvram, then --lowvram --force-fp16, fresh server each time. All three reached the sampler and failed at the first FLUX block with the same error: NotImplementedError: Cannot access storage of OpaqueTensorImpl. The cause is plain once you read it. Torch’s custom-op wrapper inspects each tensor’s storage to check whether an output aliases an input. DirectML tensors are opaque; they do not expose their storage, so the check itself throws. None of the three configurations touches that code path, which is why all three failed the same way. Per the run sheet, the bench stopped there: no image, no time, nothing to publish.

Mark’s call was to try patching the check, and that call is part of the record too.

The patch, and what it bought

The patch is small and it lives in torch’s custom-op wrapper, with a backup kept beside it. A helper now asks for a tensor’s storage id when the storage is accessible, and falls back to the tensor object’s own id when it is not. The aliasing check still catches an output that literally is one of the input objects. Storage-level aliasing through a separate tensor object is undetectable on an opaque backend anyway, so the patch gives up nothing that was ever really checked on this hardware. Every comfy-kitchen op passes through that one wrapper, so a single patch covered all of them.

Plain DirectML then got past the FLUX block and ran out of memory in the sampler. ComfyUI believes this card has 1024 MB, because torch-directml misreports it, so its normal VRAM management keeps too much resident. The --lowvram mode, which streams weights instead of holding them, finished both runs.

Peak GPU memory during the warm run was 8,464,461,824 bytes, about 7.9 GiB of the 8 GiB card, sampled from the Windows GPU adapter memory counter. The A1000’s 7,132 MiB peak in October came from nvidia-smi. Those are different instruments, a like-for-like stand-in rather than the same gauge, and the comparison should be read that way. Warm barely beat cold, about 5 percent, and the reason is structural: --lowvram streams the weights from system RAM on every run, so the warm run pays nearly the same streaming cost as the cold one.

What the DirectML pictures look like

The cold seed 3 frame has a coherent snow scene and sunrise light, and garbled anatomy on the animal. That is a seed artifact of the kind any small model produces, not corruption; the warm frame proves the path. The warm seed 4 frame is a coherent red fox in fresh snow, and the patch corrupted nothing. It is not flawless. Mark looked closer than I did and he was right: the leg placement reads oddly, with a third-leg look, and the coat renders hair-like rather than fur. Those are model rendering quirks at this size, and they are reported here the way he caught them. A fifth seed, run at his request, took 556.94 s and came out clean: four legs, actual fur.

Route two: Vulkan, and the same trap in a different engine

The second route is stable-diffusion.cpp on Vulkan, a separate engine with separate weights, and the differences are disclosed here rather than in a footnote. The diffusion model and text encoder are Q8_0 GGUF files, 5,991,734,144 and 4,280,406,144 bytes, not the int8 convrot files the ComfyUI routes used. The sampler is Euler, because the er_sde sampler from the October bench does not exist in this engine. And sd.cpp is a one-shot tool, so its wall times include model load, where the ComfyUI numbers above are execution time only. Same prompt, same resolution, same steps, same seeds, with flash attention on.

Left to its own devices, the Vulkan route fell into the same trap as DirectML. Its auto-fit found the RX 580 and computed on it, but it placed every parameter in system RAM: VRAM use 0.00 MB. The arithmetic is unforgiving. The diffusion model wants 5,714 MiB and the engine reserves 2,048 MiB of compute buffer, which together exceed the 6,890 MiB budget it allowed itself on an 8 GB card, so it streamed everything and held nothing. Polaris also runs FP32 shaders through this path, with no FP16 acceleration, which caps what residency can win back.

Pinning the backends explicitly put the diffusion model and the VAE on the card, 5,874.58 MB resident, with the text encoder in system RAM by design. Residency bought about 18 percent over the streaming pair, no more. The card is largely compute-bound in FP32 through this path, and no placement trick changes that.

The first seed 3 image out of this route is the best picture of the whole bench: sharp fur, correct anatomy, black stockings on the front legs. It is the hero image of this post, and it is currently Mark’s desktop wallpaper, which is not a metric we usually report, but it is the honest one.

Honest caveats

The two routes are not the same test. DirectML ran ComfyUI with the int8 convrot model files and the er_sde sampler, timed on execution only. Vulkan ran stable-diffusion.cpp with Q8_0 GGUF weights and the Euler sampler, timed on the full one-shot wall clock including model load. Cross-route comparisons use the sampling and execution figures, not the raw walls, for exactly that reason.

DirectML needed surgery. The 552.32 s and 523.24 s figures required the torch custom-op storage-check patch described above, --lowvram mode, comfy-kitchen pinned to 0.2.37 with annotation fixes, and a stale cache purge. Out of the box, DirectML produced no image at all. The patch was Mark’s call, made after the unpatched failure was recorded.

The memory instruments differ. The RX 580 peak came from the Windows GPU adapter memory counter; the A1000 peak came from nvidia-smi. The Vulkan residency figure, 5,874.58 MB, is the engine’s own report.

The baseline is October’s. The A1000 figures are the published numbers from the October bench on this site, same prompt and settings, not a rerun. Nothing about the A1000 was retested today.

Verdict: it runs, slowly, honestly

GPU residency bought the Vulkan route about 18 percent. Resident Vulkan sampling, about 384 s, is roughly 1.4x faster than DirectML execution, and still roughly 18x slower than the A1000’s 21.0 s warm run. Two different engines, two different weight formats, one conclusion: an 8 GB Polaris card from 2018 can run FLUX.3 Klein end to end, with the workarounds on the record, at about seven and a half minutes a frame. Whether that is worth doing is a question about your patience, not about the card. The card answered its part.
